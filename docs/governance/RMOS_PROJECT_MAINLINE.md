## 3. 长期主干

### S0｜统一现状

目标：让项目只有一个可信的当前状态。

通过条件：

- 当前代码基线明确；
- 已知问题集中在一张当前清单；
- 冲突状态已经统一或明确保留为未知；
- 董事会确认唯一下一步。

### S1｜目标架构

目标：决定系统未来的整体结构。

通过条件：

- 主要模块清楚；
- 每个模块的职责和数据归属清楚；
- 董事会批准总体方向。

本阶段不要求提前设计完所有接口、文件和代码。

### S2｜模块改造顺序

目标：把目标架构变成可执行的模块顺序。

通过条件：

- 每个模块明确保留、合并、替换或删除；
- 模块依赖和改造顺序明确；
- 董事会批准第一个试点模块。

### S3｜逐模块改造

目标：按批准顺序逐个改造模块，并保持系统可用。

每个模块通过条件：

- 核心流程实际跑通；
- 该模块内已知的严重安全、权限和数据问题已处理；
- 有可执行的回退方法；
- 其余问题已进入当前问题清单。

普通功能错误和体验问题不阻止进入下一个模块。

### S4｜系统联调与内部使用

目标：让真实使用尽早暴露问题。

通过条件：

- 主要角色各完成至少一次核心流程；
- 使用中发现的问题全部登记；
- 没有正在发生的严重安全、权限或数据损坏问题。

### S5｜受控试用

目标：在有限范围内验证系统能否持续工作。

通过条件：

- 用户、数据和机器人范围明确；
- 出现问题能够停止并恢复；
- 关键数据有可用备份；
- 董事会批准扩大范围。

### S6｜正式交付

目标：达到正式使用所需的最低可靠性。

通过条件：

- 权限不能被已知方式绕过；
- 关键数据能够恢复；
- 涉及真实机器人的场景具备可靠停止手段；
- 董事会明确批准正式启用。

## 4. 董事会与执行者权限

只有董事会可以：

- 修改长期目标或阶段顺序；
- 改变当前阶段；
- 宣布阶段通过；
- 接受残余风险；
- 批准偏离主干；
- 批准扩大试用、真实机器人或生产范围。

执行者可以：

- 完成当前批准的任务；
- 在批准任务内部自主安排低风险小步骤；
- 补充证据和实际结果；
- 登记新问题和阻断；
- 提出下一步或阶段切换申请。

执行者不得自行把“文件完成”“测试通过”“问题已登记”改写成“阶段通过”。

## 5. 任务准入

每个任务开始前必须回答：

1. 当前处于哪个主干阶段？
2. 当前阶段的唯一目标是什么？
3. 本任务对应哪个主干任务编号？
4. 本任务允许修改什么？
5. 本任务的完成条件是什么？

无法回答第 3 项时，不进入执行，按下列规则处理：

| 类型 | 处理方式 |
|---|---|
| 紧急问题 | 安全、权限、数据损坏或机器人失控风险可中断主干；只做最低限度保护，记录结果后回到原唯一下一步 |
| 必要阻断 | 不解决就无法继续主干；形成简短申请，由董事会决定是否插入当前阶段 |
| 普通支线 | 功能想法、体验优化和非紧急重构进入当前问题清单，不改变当前阶段和唯一下一步 |

所有正式任务使用 `RMOS-S<阶段>-<三位序号>` 编号。当前唯一活动任务为 `RMOS-S0-001`，对应 S0-01。

## 6. 偏离后的返回规则

发现对话、代码或文档偏离主干时：

1. 保留现场，不清理、不覆盖现有变化；
2. 记录实际工作区、分支、提交和未提交内容；
3. 说明偏离内容与当前阶段的关系；
4. 紧急风险按最低保护处理，其他事项进入阻断申请或问题清单；
5. 恢复本文件中的“唯一下一步”；
6. 只有董事会决定改变阶段时，才修改主干顺序。

普通问题不会让已批准阶段整体失效。只有以下情况允许申请重开：

- 阶段依赖的核心事实被证明错误；
- 出现严重安全、权限或数据风险；
- 董事会明确要求重开。

重开只影响能够列明的对象；无法确定影响范围时才考虑整阶段重开。

## 7. 使用中暴露问题

本项目允许普通问题在内部使用和受控试用中暴露，不以“零问题”作为阶段条件。

| 等级 | 处理 |
|---|---|
| 严重 | 可能导致越权、关键数据损坏、机器人危险动作或无法恢复；立即停止相关范围并保护现场 |
| 阻断 | 当前核心流程无法继续；进入当前阶段优先处理 |
| 普通 | 功能、体验、性能或边界问题；登记后按优先级迭代，不回退整个阶段 |

内部使用可以带着已知普通问题前进。真实机器人、生产启用和不可恢复的数据操作仍必须满足安全底线并获得董事会批准。

## 8. 任务结束与状态更新

每个任务结束必须记录：

- 主干任务编号；
- 实际改动和结果；
- 验证证据；
- 新发现问题；
- 未解决阻断；
- 建议的下一步。

执行者可更新证据、问题和实际结果；“当前阶段”“阶段状态”和“唯一下一步”的方向性改变必须有董事会原始批准。

## 11. 主干变更规则

方向性变更按以下顺序执行：

1. 执行者提出修改建议，说明原因和影响；
2. 董事会明确批准；
3. 在本文件记录批准日期、原话和变更内容；
4. 更新版本并提交，提交后新规则才生效。

阶段切换使用明确口令：`确认主干阶段 S<n> 完成，进入 S<n+1>`。含糊的“继续”“可以”只授权当前任务继续，不自动批准阶段切换。
