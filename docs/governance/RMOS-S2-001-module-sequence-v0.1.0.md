## 4. 改造顺序（由拓扑序给出）

### 4.1 排序依据

业务模块无环，**顺序不再靠经验**：按依赖拓扑序的**逆序**排——
先改被依赖最少的底层，改动不会牵连已完成的模块。

拓扑序（调用者在前）：`D → I → O → G → B → A → C → F → E → H`
**改造顺序＝其逆序**。

### 4.2 顺序表

| 序 | 模块 | 依赖的业务模块 | 测试用例 | 状态 |
|---:|---|---|---:|---|
| — | **A** 身份与访问控制 | F | 260 | ✅ **已完成**（S3 试点） |
| 1 | **H** 证据与评估 | 无 | **3** | ⚠️ **须先补测试**，见 §4.3 |
| 2 | **E** 任务执行 | H | 42 | |
| 3 | **F** 教学 | E、H、D | 96 | |
| 4 | **C** 知识 | 无 | 21 | |
| 5 | **B** 机器人资产 | A | 182 | |
| 6 | **G** 训练 | B、C、H | 87 | |
| 7 | **O** 应用编排 | G | — | 含「是否保留 O」的判定 |
| 8 | **I** Agent 运行时 | C | 106 | 含三张并表 + 状态落库 |
| 9 | **D** SOP 与维保 | C | 29 | |
| 10 | **S1／S2／S3** 支撑三模块 | 互相 | 116 | 一并处置 mock／仿真三角（§1.1） |

> **A 已在试点中完成**，不再占序位。其余按拓扑逆序。
> 该顺序保证：改任一模块时，**它依赖的模块要么已改完，要么不在业务模块内**。

### 4.3 两个硬约束（不变）

**约束一：H 必须先补测试。**
H 排第 1 位是依赖决定的（它不依赖任何业务模块），但它
**24 条路由、7 张表、1,927 行代码只有 3 个测试用例**——全场最薄。
**补足行为级测试之前不得改 H**。若不愿先补测试，则把 H 后移，先做 C（依赖同样为空、有 21 个用例）。

**约束二：I 的并表需要迁移。**
S1 裁决三的三张并表涉及 Alembic 迁移与数据搬运，须在本机 PostgreSQL
实测 `upgrade → downgrade → upgrade` 三步。

### 4.4 每个模块完成后的固定动作

按 S3 试点的教训（口径错误直到试点才暴露），每个模块完成后：

1. 用同一脚本（`evidence/2026-09-05-layered-dependency-measure.py`）重测依赖，
   确认没有产生新的跨模块边；
2. 全量测试通过数**只许增不许减**；
3. 结构改动与功能改动**分属不同提交**，各自可单独回退。

**不再要求每个模块后重排顺序**——拓扑序已由无环依赖图给出，稳定。

## 5. 试点模块 A（**已完成，存档**）

> 试点已于 2026-09-05 完成，结果见 `RMOS-S3-001-pilot-module-A-result-v0.1.0.md`：
> **功能目标（M-13）达成，结构目标（解环）失败**，并因此触发本次定向重开。
> 以下内容为当时的选择理由与范围，存档供追溯。

### 5.1 为什么是 A

| 理由 | 依据 |
|---|---|
| 它是解环的唯一入口 | A 入度 9（全场最高），几乎所有环经过它；不先解 A，后面 11 个模块都没有干净的顺序 |
| 安全网最厚 | 260 个测试用例，全场第一 |
| 试点动作本身不改行为 | 移动文件 + 改 import，行为不变，风险可控 |
| 有实质价值，不是纯整理 | 试点范围含 **M-13 收口**（见 §5.2），能关掉一个仍存在的问题 |

> **与 S1 §3.2 的一致性说明**：S1 写过「移动文件不产出功能价值，不应单独为整理而整理」。
> 本试点**不违反**该原则——它不是为整齐而搬家，而是为解开 1,934 个环的死结；
> 且同批包含 M-13 这项功能性收口。**若只做搬家不做 M-13，则该原则适用，应当合并到别的批次。**

### 5.2 试点范围（**严格限定**）

| # | 动作 | 性质 |
|---|---|---|
| 1 | `session_initializer` → **新建模块 O**；`class_membership`／`teacher_monitor` → **F** | 结构，不改行为 |
| 2 | `robot_visibility` → **B**（归属修正，§2.1） | 结构，不改行为 |
| 3 | 根目录 5 个身份文件（`authz_guard`／`access_control`／`ownership`／`login_throttle`／`audit_event_service`）归位到 A | 结构，不改行为 |
| 4 | `ensure_task_scope` 改收 `owner_user_id`；`EventType` 移至共享位置 | 结构，不改行为 |
| 5 | **M-13 收口**：角色事实源统一、auditor 职责分离（`auditor` 当前仍持 `approvals:grant`／`reject`） | 功能与安全 |

| 7 | **确认 O 是否保留**：若 O 内只有 `session_initializer` 且无第二个候选，改为拆回三模块 | 判定 |

**完成第 6 项后必须重跑依赖聚合并把结果提交董事会**——第 2–12 位的顺序据此确认或调整（§4.1）。

**不在试点范围内**：A 的租户隔离（M-12）、其余 11 个模块的任何改动。

### 5.3 完成条件（对齐主干 §3 的 S3 每模块通过条件）
