### 2.1 `robot_projects` 是数据模型缺陷，不是代码疏漏

该表**没有任何归属字段**，与 M-01 的五张表同型。按裁定 §9-2 已确立的先例处置：
补 `created_by_user_id` + `school_name`，迁移 `20260906_c_project_owner`，
本机 PG 实测 `upgrade → downgrade → upgrade`。历史行不回填（NULL＝系统内置，仅管理员可见）。

**与教学表的差异**：此处 `school_name` **参与可见性过滤**，不是纯预留维度——
机器人项目的跨校泄漏是实测确认的缺陷，不是理论风险。

### 2.2 两个容易做错的地方

**一、检索过滤必须在 SQL 层。**
若先取回再在 Python 侧筛，pgvector 的 `LIMIT` 会先被他人条目占满，
同校条目反而被挤掉——过滤"生效"了，可用性却没了。
keyword / pgvector / python 三条召回路径全部加了 SQL 条件。

**二、切块必须继承项目归属。**
只在项目层过滤是不够的：切块进了 `ai_knowledge_chunks` 后，
检索层照样能把内容漏给他校。项目层与检索层要同时堵。

### 2.3 错误码口径（本模块同时用到三种，不能混）

| 场景 | 码 | 依据 |
|---|---|---|
| 资源确实不存在 | **404** | C-API-01 |
| 读路径越权 | **404** | 不泄露存在性（`robot/visibility.py` 口径） |
| **写路径越权** | **403** | 目标对象已由调用方确认存在（`ownership.py` 口径） |

G4 修 C-API-01 时最需防的回归就是"顺手把越权也改成 404"——
三条跨校用例复跑通过，口径未破。

## 4. M-23 的根因已查清（S0 清单中一直是「仍存在」）

实测结论：

1. 知识的创建／提交／批准**只更新内存与本地 JSON**；
2. 批准成功后**不触发切块、向量生成或任何数据库写入**；
3. 检索读的是**另外两张数据库表**；
4. 实测批准前后，两张检索表记录数**完全相同**。

**审批链路与检索底料是两套完全不相连的存储。** 这是 M-23 的根因，
也与 M-16（内存代替落库）同源。

打通它属**架构级改动**：要么审批链路落库，要么检索改读 JSON。
两个方向都会牵动 M-16 与 M-19，**需董事会先定方向**，不宜在模块 C 内夹带。
