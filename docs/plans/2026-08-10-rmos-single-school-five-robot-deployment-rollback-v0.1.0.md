# R-MOS 单校五台真机上线与回滚计划

> **For Codex:** 实施本计划时必须使用 `superpowers:executing-plans`，逐项建立测试、实施、演练、证据和提交记录；未经用户许可不得推送。

**Goal:** 在不绕过教师确认、现场检查和物理急停的前提下，把R-MOS分批开放给一所学校的1,050个账号和5台真机，并能在安全、权限、数据或稳定性异常时快速停止和恢复。

**Architecture:** 软件采用“上一稳定版本持续可用、新版本按班级分批开放”的方式；数据库变更只允许向前兼容，稳定7天后才能删除旧结构。5台机器人先全部只读，再按1、2、3、5台逐批开放受控动作；任何阶段都保留单机和全局非停止动作关闭开关，教师确认的软件停止保持可用，物理急停独立于平台。

**Tech Stack:** Docker Compose、Nginx、FastAPI、PostgreSQL、MinIO、React、OpenTelemetry、Prometheus；发布产物使用固定版本和SHA-256校验，不使用浮动版本。

## 1. 当前基线与生产阻断

当前`docker-compose.yml`只能作为开发基线，禁止直接用于学校生产环境，原因如下：

- 数据库默认密码为`changeme`，应用默认密钥为`dev-only-change-me`，`DEBUG`默认开启。
- AI模拟回退默认开启，MinIO使用`latest`浮动版本。
- 数据库、后端和对象存储端口直接暴露，未配置学校TLS入口。
- 后端和前端没有完整就绪检查，没有正式监控、告警、备份、恢复和版本回滚脚本。
- 当前没有并行保留上一稳定版本的能力，也没有按班级和机器人分批开放的正式开关。
- 正式`.venv`、预生产环境、5个机型和20场课堂试点尚未完成。

“上一稳定版本”必须是通过B1、B2和安全门禁的不可变发布包。当前演示版本存在默认密钥、权限和真机接入缺口，不能作为生产回滚目标。首次上线若还没有合格的旧版本，必须先制作一个“权限合格、核心教学可读、全部真机动作关闭”的安全基线包；该基线包未通过验收时，D1保持阻断。

因此，本文件是实施目标和上线门禁，不代表当前系统已经具备生产上线能力。

## 2. 角色、授权与时间要求

| 角色 | 上线责任 | 回滚责任 | 最长响应时间 |
|---|---|---|---:|
| 发布负责人 | 核对版本、门禁和批次，宣布开始或停止 | 决定软件批次回退 | 告警后2分钟 |
| 运维负责人 | 部署、监控、备份、切换和恢复 | 在5分钟内切回上一稳定版本 | 告警后1分钟 |
| 后端与数据负责人 | 核对兼容性、迁移和数据一致性 | 决定保留、对账或恢复数据 | 告警后5分钟 |
| 安全负责人 | 核对权限、审计和密钥 | 安全事件时强制停止发布 | 告警后1分钟 |
| 机器人负责人 | 核对适配器、状态、动作目录和隔离 | 关闭单机或全部非停止动作入口，保留教师确认的软件停止 | 告警后30秒 |
| 学校现场安全负责人 | 核对人员、围栏、急停和现场状态 | 必要时立即按下物理急停 | 立即 |
| 学校课程负责人 | 确认班级、课表、教师和学生范围 | 暂停课堂或切回仿真教学 | 告警后5分钟 |

以下决定不得由一人单独完成：

- 开放任一真机受控动作：机器人负责人和学校现场安全负责人共同签字。
- 全量开放：发布负责人、学校课程负责人、学校信息化负责人和现场安全负责人四方签字。
- 恢复数据库或丢弃上线后数据：发布负责人、数据负责人和学校信息化负责人三方签字。

## 4. 分批上线方案

采用“班级为最小软件批次、机器人为独立硬件批次”，不随机拆分同一班学生。同一机器人同一时刻只允许一个软件版本拥有受控资格。

| 阶段 | 人群与比例 | 真机范围 | 最短观察期 | 进入条件 | 退出条件 | 失败处理 |
|---|---|---|---:|---|---|---|
| D0 影子观察 | 0名课堂用户，0%；仅7名项目人员 | 5台全部只读，0台受控 | 72小时 | 上线清单100%完成；回滚演练通过 | 5台在线率≥99.9%，跨机消息0条，监控数据连续率100% | 保持旧版；任何真机消息隔离问题立即停D0 |

| D2 四班试用 | 100名学生+4名教师+1名管理员，共105/1,050=10.0% | 2台受控，另3台只读 | 48小时且完成4场课 | D1连续24小时无P0/P1问题 | 4/4场完成；严重越权0次；普通请求达到M-07 | 撤销D2新增班级和第2台机器人，保留已验证D1范围 |

阶段晋级规则：

- 观察期和业务样本必须同时满足；时间到了但样本不足，不得晋级。
- 每阶段结束后由发布、课程、安全三方签字；真机数量增加时另需机器人负责人签字。
- P0或P1问题出现1个，当前观察计时清零；修复并重跑相关测试后从该阶段重新开始。
- D4稳定7天后才可宣布“正式上线”，但仍需每月执行一次恢复演练。

本计划中的“关闭软件动作”统一指：30秒内关闭启动、复位、回零和所有预定义运动动作；教师逐次确认的软件停止保持可用。若软件停止入口本身不可信或机器人行为异常，现场人员立即使用物理急停。

## 6. 回滚条件与处理级别

### 6.1 处理级别

| 级别 | 触发范围 | 必须动作 | 时间上限 |
|---|---|---|---:|
| L0 现场安全停止 | 急停失效、人员进入危险区、机器人行为异常 | 现场人员立即物理急停；平台动作开关关闭 | 立即；软件关闭≤30秒 |
| L1 单机或单班撤销 | 单机器人遥测、动作或单班体验异常 | 撤销对应机器人或班级的新版本资格，回到只读、仿真或旧版 | ≤5分钟 |
| L2 当前批次回滚 | 性能、错误率、页面或业务流程达到回滚阈值 | 当前D阶段新增人群全部切回上一稳定版本 | ≤5分钟 |
| L3 全版本回滚 | 越权、未批准动作、跨机器人、审计缺失或数据不一致 | 全部用户切回上一稳定版本；真机全部回到只读 | ≤10分钟 |
| L4 数据恢复 | 数据损坏且无法通过对账修复 | 停止写入，从可信备份恢复并核对 | RTO≤30分钟、RPO≤15分钟 |

### 6.2 满足任一即执行的条件

- [ ] 未批准动作、AI直接动作、重复动作或跨机器人执行出现1次。
- [ ] 物理急停、厂家安全项或现场检查出现1次失败。
- [ ] 严重越权成功1次，或拒绝审计缺少1条真实资源编号。
- [ ] 1,000组迁移或报告记录出现1组attempt_id不一致。
- [ ] 服务错误率>1%持续1分钟，或普通请求p95>3秒持续1分钟。
- [ ] 核心流程成功率<98%，或连续5次核心流程失败。
- [ ] 审计完整率<100%，或100次篡改测试漏报1次。
- [ ] 单个学生等待>15分钟，或连续2场课堂p95等待>10分钟。
- [ ] 监控中断>5分钟、备份年龄≥24小时或存储占用≥90%；此类先停止新增训练，不自动恢复旧数据。

安全条件优先于软件回滚：机器人未确认处于安全状态前，不得重启适配器、重新发送命令或切换控制版本。

### 7.2 数据处理规则

1. **默认保留新数据：** 若数据结构兼容且校验通过，切回上一版时保留上线后产生的数据；禁止为了方便直接还原全库。
2. **隔离可疑数据：** 若仅部分记录异常，立即停止对应写入，导出事件前后15分钟记录到隔离区；原始记录只读保留。
3. **独立恢复验证：** 先把最近可信备份恢复到独立环境，核对数据库、对象、审计、动作和报告校验值，不覆盖生产。
4. **对账优先：** 能在30分钟内明确修复范围时，生成逐条对账清单并由三方签字后修复；修复历史必须追加记录，不覆盖审计。
5. **全库恢复最后使用：** 只有无法对账且继续运行会扩大损失时才允许恢复生产；必须满足RPO≤15分钟并明确列出丢失记录。
6. **动作数据不得补发：** 回滚、恢复或重启后，所有未完成命令进入“状态不明/人工核对”，自动重发次数必须为0。
7. **旧结构删除：** D4稳定7天、完成一次备份恢复且上一版不再需要后，才允许单独发布删除旧结构的版本。

### 7.3 回滚后的重新开放

- 先恢复只读访问并观察30分钟；错误率<0.1%、权限异常0次、审计完整率100%才可恢复写入。
- 写入恢复后观察2小时；核心流程成功率≥99%才可重新申请D阶段。
- 真机必须重新执行现场检查和教师确认；受控资格不得随软件恢复自动开启。
- P0/P1原因未关闭、受影响测试未重跑或证据不全时，不得重新上线。
