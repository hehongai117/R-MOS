## 0. 董事会决议摘要

R-MOS 后续工作改为“先完整认识系统，再决定目标架构，最后分层改造”。本指令批准前，不改变现行规则；本指令批准后，除紧急安全事件外，暂停既有常规功能开发和局部重构，按下列顺序推进：

1. 固定新的完整审计基线；
2. 完成 A0 至 A6 七个“代码只读”审计阶段，每阶段单独出报告并由用户确认；
3. 使用标准化研究技能和统一评分模型完成 R0 开源参考架构研究；
4. 根据 A0–A6 与 R0 的证据，在 R1 形成目标架构方向方案；
5. 只有 R1 获批后，才另行编制详细改造计划；
6. 实际改造严格按“架构 → 模块 → 文件 → 代码”推进，不允许倒序开始。

本指令不决定具体模块怎样拆、接口怎样改、数据表怎样迁移、采用哪一个开源组件、投入多少人日或何时上线。这些属于后续 R1 和详细改造计划的范围。

## 1. 背景与问题定义

### 1.1 当前偏离

既有 Phase 0–2 完成了规则修复、六链路审查和部分安全设计；Phase 3 已开始修改应用代码。2026-08-26 的复核表明，完整功能清单和全项目架构审计尚未完成，局部修复已经先行，产生以下治理风险：

- 审计基线随修复变化，事实、历史和新行为容易混淆；
- 同一根因被拆成多个“新发现”，问题数量和优先级失真；
- 局部安全修复改变前端或其他链路，引入新的回归；
- 旧实施计划提前指定技术与工作包，但缺少完整功能地图的支持；
- 文件和代码先动，模块边界和目标架构仍未统一；
- 自动测试数量较多，但部分测试不能证明真实权限、归属或交付能力。

### 1.2 一句话目标

由项目决策者通过一套可复现、分阶段、只读优先的完整审计，获得 R-MOS 的真实功能地图、问题总表和开源参考证据，从而在不丢失有效资产的前提下批准一套可逐层迁移、可验证、可回滚的目标架构方向。

### 1.3 第一受众

- 第一受众：项目决策者，用于批准审计阶段、目标架构方向和是否重写；
- 第二受众：后续架构师与开发者，用于理解边界、证据和阶段门禁；
- 第三受众：独立复核者，用于在不依赖聊天上下文时复现结论。

## 4. 总体阶段顺序

```text
D0 董事会方向批准
  ↓
A0 基线、事实源与审计治理
  ↓
A1 全系统功能与资产清单
  ↓
A2 用户角色、业务流程与产品闭环
  ↓
A3 当前架构、模块、依赖与数据模型
  ↓
A4 身份、安全、控制、AI 与实时通道
  ↓
A5 测试可信度、部署、恢复与交付能力
  ↓
A6 总问题表、重复归并与改造/重写决策输入
  ↓
R0 开源参考架构研究
  ↓
R1 目标架构方向方案
  ↓
P0 详细改造计划（本指令不包含）
  ↓
未来实施：架构 → 模块 → 文件 → 代码
```

### 4.1 阶段推进规则

- 每个阶段只维护一个“当前正式报告”；已提交、已复核或已批准版本不可覆盖，必须保留版本、批准人、批准日期和被替代关系；原始证据可有多个附件；
- 每阶段开始前必须固定提交、工作目录、工具权限和排除项；
- 每阶段结束后先做内部检查和无上下文读者测试，再提交给用户；
- 只有用户回复“确认 Audit Ax”或“确认 Reference R0/R1”后才能进入下一阶段；
- 发现 P0 不等于自动获得真实环境隔离或修复授权；应先停止当前审计动作、保存证据并提交隔离建议，等待董事会决定；
- 任何阶段的文档通过都不能提升软件、预生产、真机或课堂验收状态。

### 4.2 阶段重开与连锁失效

- 发现重大漏项、审计基线变化，或后续证据推翻已批准阶段的关键结论时，必须提出重开申请；
- 重开点是“最早受影响阶段”：例如 A4 发现 A1 漏掉入口，应重开 A1，而不是只改 A4；
- 从重开点起，依赖该结论的后续批准自动转为 `SUSPENDED`，不得继续作为决策依据；
- 未受影响部分可引用原报告，受影响对象、分母、发现和门禁必须增量复核；若无法证明影响边界，则整阶段重审；
- 重开报告必须记录触发证据、影响图、保留项、重审项和后续失效范围；
- 用户以 `确认重开 Audit <阶段> <原因编号>` 批准重开，以正常阶段批准口令重新批准；重开阶段重新批准后，所有后续阶段仍保持 `SUSPENDED`，必须按原顺序逐阶段完成影响复核、发布新版本或“结论不变”增量说明，并逐阶段重新获得正常批准，不能自动恢复；在恢复到原最远阶段前不得开展新阶段。

## 5. 正式审计章程

### 5.1 审计对象

完整审计必须覆盖：

1. 产品角色、页面、导航、按钮和用户流程；
2. HTTP 接口、WebSocket、后台任务、脚本和命令入口；
3. 服务层、适配器、AI 工具、审批、审计和证据链；
4. ORM 模型、迁移、存储目录、对象存储和数据生命周期；
5. 机器人型号、实例、资产、遥测、控制、停止和异常恢复；
6. 单元、集成、端到端、浏览器、预生产、真机和课堂测试材料；
7. 依赖、容器、网络、密钥、备份、恢复、监控和运行手册；
8. 现行、历史、归档、缺失和相互冲突的文档声明。

### 5.2 审计禁令

A0–A6 期间禁止：

- 修改应用、测试、依赖、迁移、数据或部署配置；
- 为了让检查通过而放宽断言或改变证据口径；
- 把旧报告数字直接写成当前结果；
- 把自动测试通过写成权限、恢复、真机或课堂通过；
- 使用一个局部样例代表整条链路或全系统；
- 删除或覆盖用户现有改动和历史证据；
- 绕过验证码、访问限制、许可证或安全警告；
- 未经许可向外部服务发送私有代码、依赖清单、数据或身份信息；
- push、合并或启用生产功能。

本章所称 A0–A6 为“代码只读审计”：只允许写报告与证据，不允许修改被审代码。隔离写入探针不是默认审计动作，必须通过单独的探针批准，且完整登记目标环境、网络出口、测试数据、前后快照、清理命令和清理结果。探针只能连接临时、可销毁环境，禁止连接真机、正式数据库、正式对象存储、生产/预生产服务或任何真实外部控制通道；无法证明隔离时不得执行。

### 5.3 事实、推断与未知

| 类型 | 定义 | 报告要求 |
|---|---|---|
| FACT | 当前代码、配置、命令、数据结构或可复现运行直接证明 | 必须给出提交、路径和复现方法 |
| INFERENCE | 多项事实支持，但尚未直接复现 | 必须写失效条件和最小验证方法 |
| UNKNOWN | 当前证据不足或外部条件缺失 | 不评分为已通过或已失败，登记所需证据 |
| HISTORICAL | 只在过去提交或环境成立 | 必须带日期、提交和不可外推说明 |

### 5.4 证据等级

证据等级完全沿用 `docs/testing/ACCEPTANCE_CHARTER.md`：

- E0：计划、说明、注释和历史报告；
- E1：当前静态代码、配置、数据结构、Git 历史和自动化测试；
- E2：与交付配置一致的预生产、浏览器、性能、断网和恢复证据；
- E3：真实机器人安全区证据；
- E4：真实课堂证据。

本审计不得重新定义或降低上述等级。A0–A6 原则上只形成 E0/E1 结论；缺少 E2–E4 时必须保持 BLOCKED 或 NOT_RUN。

### 5.5 严重度

| 等级 | 判定标准 | 默认动作 |
|---|---|---|
| P0 | 可造成未授权控制、凭据泄露、远程执行、供应链投毒、成绩/证据篡改、跨租户重大泄露、安全联锁失效、真实机器人安全风险或数据不可恢复 | 立即登记、停止当前审计动作并提出隔离建议；真实环境隔离和紧急修复分别由用户批准 |
| P1 | 关键业务错误、稳定越权路径、主链路中断或生产门禁缺失 | 纳入第一改造波候选，不在审计期直接修 |
| P2 | 有限条件缺陷、可恢复功能问题、明显技术债或证据缺口 | 纳入模块改造候选 |
| P3 | 低影响一致性、文档、可维护性或体验问题 | 进入普通待办候选 |

严重度描述影响，不代表修复顺序；修复顺序必须同时考虑根因、依赖和改造层级。

### 5.6 发现编号与唯一问题表

- 阶段发现编号：`A<阶段>-<领域>-<三位序号>`，例如 `A4-AUTH-001`；
- 原有 `AUTH-*`、`CTRL-*` 等编号保留为历史别名，不直接复制成新问题；
- 每条新发现必须先查唯一问题表，判定为 `NEW`、`EVIDENCE_FOR_EXISTING`、`DUPLICATE` 或 `CONTRADICTION`；
- 同一根因在多个入口出现时，登记一个主问题和多个受影响实例；
- A6 前重复问题必须归并为 0 个未裁决重复项。

发现状态统一使用：

| 状态 | 含义 |
|---|---|
| NOT_REVIEWED | 已进入范围，但尚未完成取证 |
| CONFIRMED_OPEN | 当前事实直接证明且尚未处理 |
| INFERRED_OPEN | 推断成立条件已记录，仍待直接验证 |
| UNKNOWN | 当前证据不足或外部条件缺失 |
| DUPLICATE | 已归并到另一个主问题，不单独计数 |
| CONTRADICTED | 新证据推翻了旧结论，保留更正链 |
| HISTORICAL | 只描述过去提交或环境 |
| RESOLVED | 后续改造完成并按要求复验；A0–A6 不得仅凭文档设置此状态 |

### 5.7 正式发现必填字段

- ID、标题、阶段、领域；
- FACT / INFERENCE / UNKNOWN / HISTORICAL；
- P0–P3；
- 当前状态；
- 受影响角色、功能、数据和设备；
- 根因假设及失效条件；
- 代码/配置/文档路径；
- 复现命令、输入、输出和执行时间；
- 证据等级；
- 与既有问题的关系；
- 不处理的后果；
- 最小验证方法；
- 独立复核结论；
- 后续决策，不在审计报告内写详细修复步骤。

### 5.8 独立复核

- 每阶段至少一次由未参与主要取证的读者复核；
- Claude Code 或其他 CLI 只允许受限只读模式，必须记录认证状态、工具范围、退出码、费用和工作区前后差异；
- 独立复核意见必须由主审重新验证，不能直接采信；
- 工具版本可运行不等于已登录、已读取或已完成审查。

### 5.9 紧急例外

A0–A6 期间只有同时满足以下条件，才可申请暂停审计并处理紧急问题：

1. 已确认 P0，且继续保留当前行为会扩大真实损害；
2. 有明确受影响范围和临时隔离措施；
3. 用户单独批准紧急修复；
4. 使用独立分支和独立报告；
5. 修复后重新固定审计基线，受影响阶段重新执行。

批准前只允许最低限度的无外部副作用保护：停止主审自己启动的临时命令或临时服务、结束隔离探针、保存现有证据、停止继续访问风险入口。停用共享/正式服务、修改配置或防火墙、撤销他人凭据、冻结账号、断开设备、改变生产数据等真实环境隔离，必须先获得 `批准紧急隔离 <Finding_ID>`；代码或数据修复另需 `批准紧急例外 <Finding_ID>`。若人身安全存在正在发生的紧迫危险，现场人员按既有安全规程和物理急停处置，本文件不取代现场安全责任。

### 5.10 治理角色

| 角色 | 职责 | 不得做 |
|---|---|---|
| 董事会/用户 | 批准本指令、阶段推进、紧急例外、R1 和最终改造路线 | 不用口头模糊同意替代明确批准口令 |
| 主审 | 固定范围、取证、归并发现、形成报告和复验独立意见 | 不把建议、工具输出或历史数字直接写成事实 |
| 独立复核者 | 在受限权限下寻找遗漏、矛盾和不可复现结论 | 不直接修改应用或替主审作最终裁决 |
| 证据保管责任 | 保证原始输出、脚本、时间、环境和提交可恢复 | 不只把证据留在聊天或临时目录 |
| 后续架构负责人 | 在 A6+R0 后编制 R1，并维护决策追溯 | 不在审计阶段提前定模块、接口或技术采用 |
| 后续实施人员 | R1 和详细计划批准后按层级执行 | 不跨过架构、模块和文件层直接改代码 |

具体人员可在各阶段报告中登记，但角色不得空缺：主审和独立复核者必须是两个不同的执行上下文；证据保管责任可由主审兼任，但必须把正式证据写入仓库约定路径，不能留在临时目录。

## 6. A0–A6 审计阶段定义

### A0｜基线、事实源与审计治理

**目标：** 固定一个所有后续报告都能恢复的审计起点。

**必须检查：** Git 基线、工作区、现行规则、ADR、计划、归档、环境、工具、外部条件、旧发现导入规则。

**启动安全初筛：** A0 首个工作批次、最多 4 小时内优先完成暴露筛查，只回答是否存在必须立即隔离的 P0 迹象，不替代 A4 全面审计。最低覆盖公网入口、未授权机器人控制、仓库与部署材料中的密钥暴露、跨校数据访问、生产启用状态和安全联锁状态。发现风险时先停止当前审计动作、保存证据并按第 5.9 节申请隔离或紧急修复，不在 A0 展开常规修复。

**退出门禁：**

- 固定唯一提交和只读工作区；
- 完成启动安全初筛，所有命中项已登记并完成必要隔离决定；
- 事实源分类覆盖率 100%；
- 悬空引用和冲突全部登记；
- A1 清单范围及排除项获用户确认；
- 应用、测试、配置变化 0 个文件。

**报告：**《A0 基线与事实源审计报告》。

### A1｜全系统功能与资产清单

**目标：** 回答“项目实际有什么”，不评价目标架构。

**必须清点：**

- 角色和账号类型；
- 前端路由、页面、主要交互和死链；
- HTTP/WebSocket/文件入口；
- 服务、后台任务、脚本和适配器；
- 数据模型、迁移和存储；
- 机器人、3D、SOP、任务、训练、证据、报告、AI、审批和审计能力；
- 测试和文档声明。

每一项分成两列，避免把“代码存在”写成“真实可用”：

- 实现状态（互斥）：`IMPLEMENTED`（存在可达实现）、`PARTIAL`（主路径缺少必要步骤）、`DEMO_ONLY`（只在样例/模拟入口成立）、`UNUSED`（存在但无可达消费者）、`DUPLICATE`（由另一个主项覆盖）、`DEPRECATED`（有明确弃用证据）、`UNKNOWN`（无法判断）；
- 验证等级：`E0`、`E1`、`E2`、`E3`、`E4` 或 `NOT_VERIFIED`，沿用验收总纲定义。

状态按上述顺序判定并记录唯一主状态；重叠属性写入备注，不得再造第二个主状态。`IMPLEMENTED + E0/E1` 只表示实现存在或自动证据成立，不得写成生产、真机或课堂“可用”。

**退出门禁：** M-AUD-01 达标；所有清单项有唯一编号和证据来源；未分类项为 0。

**报告：**《A1 全系统功能与资产清单报告》。

### A2｜用户角色、业务流程与产品闭环

**目标：** 回答“功能怎样组合成真实用户流程”。

**最低流程：** 注册/入校、教师建班、学生加入、SOP 制作发布、任务下发、训练执行、证据生成、评分、报告、维保、机器人控制、异常停止、审批和审计回放。

每条流程必须记录入口、角色、前置数据、关键状态、成功输出、失败路径、跨模块依赖和当前证据。

**退出门禁：** A1 中所有面向用户的功能均映射到至少一条流程或明确标记为孤立功能；关键流程的断点和重复链路全部登记。

**报告：**《A2 用户角色与业务闭环审计报告》。

### A3｜当前架构、模块、依赖与数据模型

**目标：** 回答“系统为什么形成当前行为，以及模块是否有可替换边界”。

**必须检查：** 进程与部署拓扑、前后端边界、模块责任、调用方向、共享状态、数据所有权、重复模型、循环依赖、外部依赖、扩展点和删除边界。

**退出门禁：**

- A1 每项功能均能定位到当前模块和数据；
- 所有跨模块数据写入点有所有者；
- 重复模型、共享状态和不可替换边界均登记；
- 不在本阶段决定目标目录或新接口。

**报告：**《A3 当前架构与数据边界审计报告》。

### A4｜身份、安全、控制、AI 与实时通道

**目标：** 完整审查所有跨领域安全和机器人控制边界。

**必须覆盖：** 身份签发、角色、学校/班级/教师/学生/机器人归属、读写拒绝、审批、审计、AI 工具、引用、WebSocket、遥测、命令状态机、停止、断网、重试和真机边界。

**退出门禁：** 100% 非公开入口进入身份与对象矩阵；所有写入口、实时订阅和机器人动作均有当前结论或 UNKNOWN；严重越权和未审批动作不得被测试绿灯掩盖。

**报告：**《A4 安全、控制与实时通道审计报告》。

### A5｜测试可信度、部署、恢复与交付能力

**目标：** 回答“现有证据能证明什么，系统能否稳定交付”。

**必须覆盖：** 测试收集和断言质量、假绿/空转、环境副作用、构建、依赖、密钥、容器、日志、监控、备份、恢复、升级、回滚、断网、预生产、真机和课堂证据。

**退出门禁：** 每项现有 PASS 都能追到提交、环境、命令和原始输出；无法复现的结论降级为 HISTORICAL 或 UNKNOWN；E2–E4 缺失不得提升。

**报告：**《A5 质量、运行与交付能力审计报告》。

### A6｜总问题表与改造决策输入

**目标：** 将 A0–A5 归并成董事会可决策的单一事实包。

**必须产出：**

- 唯一功能地图；
- 唯一问题表；
- 根因与受影响实例；
- 问题依赖图；
- 保留、删除、重构、局部重写和整体重写候选；
- 开源研究需要回答的问题清单；
- 当前继续修补、渐进改造和整体重写三条路线的输入条件。

**退出门禁：** 重复发现未裁决数为 0；所有 P0/P1 有证据等级和影响范围；所有候选决策都能追到 A0–A5。

**报告：**《A6 完整审计总报告与架构决策输入》。

## 7. R0 开源参考架构研究章程

### 7.1 研究原则

- 研究对象是“可借鉴的设计”，不是寻找一个整套替换 R-MOS 的母版；
- 业务匹配和安全边界高于星标数量；
- “最新”指当前仍被维护、近期有稳定发布或明确维护承诺，不等于创建时间最新；
- “成熟”必须由版本历史、贡献者、发布、治理、文档、测试和采用证据共同支持；
- “活跃”必须看最近 12 个月提交、发布、贡献者和问题响应，不能只看 `updated_at`；
- 任何许可证不明、仓库已归档、关键文档缺失的项目不得成为主参考；
- 只借鉴设计也要记录来源；复制代码、引入依赖或部署服务必须另过许可证审查和 ADR。

### 7.2 研究技能工作流

R0 正式开始后按以下技能链执行：

1. `research`：建立研究域、初始候选和字段框架，生成 `outline.yaml` 与 `fields.yaml`；
2. `research-add-items`：从 GitHub、基金会目录、论文/官方文档补充候选并去重；
3. `research-add-fields`：在第一批试研后补充遗漏字段，不得删除已确认的硬门槛；
4. `research-deep`：按批次对每个候选独立研究，输出结构化 JSON，保留 `[uncertain]`；
5. `research-report`：汇总全部字段，跳过不确定值，生成正式研究报告；
6. 主审根据原始 JSON 和官方证据生成评分矩阵，不能只根据汇总文字评分。

推荐目录（R0 批准后创建，本指令不创建）：

```text
docs/research/rmos-open-source-reference/
├── outline.yaml
├── fields.yaml
├── results/
│   └── <project>.json
├── report.md
└── decision-matrix.md
```

### 7.3 研究域与初始候选来源

| 研究域 | R-MOS 问题 | 初始种子，仅用于发现 |
|---|---|---|
| 平台与模块化单体 | 后端分层、模块责任、配置、迁移、测试和部署 | FastAPI 官方模板、成熟 Python 模块化项目 |
| 教学与学习管理 | 学校、班级、教师、学生、作业、尝试、成绩和报告 | Moodle、Open edX、Frappe LMS 等 |
| 机器人资源与适配器 | 型号、实例、能力、适配器和统一动作边界 | Open-RMF、openTCS、Viam 等 |
| 设备、数字孪生与遥测 | 设备身份、当前/期望状态、订阅隔离和告警 | Eclipse Ditto、BaSyx、ThingsBoard、OpenRemote 等 |
| 工作流、审批与状态机 | 长流程、人工确认、幂等、恢复和历史 | Temporal、Flowable 等，仅研究语义 |

| 仿真与机器人安全 | 仿真、碰撞、动作限制和测试 | Gazebo、MoveIt 等，不能替代厂家安全证据 |

以上项目来自既有计划和初步框架，不表示当前活跃、适配或获准采用。R0 必须重新验证。

### 7.4 候选发现方法

每个研究域至少使用四类来源：

1. GitHub 仓库和 Search/API：按主题、语言、星标、更新时间、非归档状态生成候选；
2. 基金会或维护组织的正式项目目录：ROS、Eclipse、Linux Foundation/CNCF、项目官网；
3. 官方架构文档、发布日志、安全策略和路线图；
4. R-MOS 既有计划中的候选项目，全部重新评分。

GitHub 数据采集遵循官方能力：仓库元数据可提供创建、推送、星标、分支、归档等字段；统计接口可提供最近一年提交和贡献者活动；发布接口提供稳定版本与发布日期；许可证接口只能识别仓库许可证，不能代替依赖许可证审查；依赖图可辅助判断被依赖情况和供应链风险。基础依据：

- [GitHub repository statistics](https://docs.github.com/en/rest/metrics/statistics)
- [GitHub repository endpoints](https://docs.github.com/en/rest/repos/repos)
- [GitHub releases](https://docs.github.com/en/rest/releases)
- [GitHub licenses](https://docs.github.com/en/rest/licenses/licenses)
- [GitHub dependency graph](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph)
- [OpenSSF Scorecard](https://scorecard.dev/)

### 7.5 硬门槛

候选满足全部硬门槛后才进入 100 分评分：

| Gate_ID | 门槛 | 失败处理 |
|---|---|---|
| OSS-G1 | 官方仓库可定位，未被归档或禁用 | 淘汰；若被行业标准替代，可仅作历史参考 |
| OSS-G2 | 对四种使用方式给出初步许可证结论：只借设计、复制代码、引入依赖、部署服务分别判断，并覆盖逐文件例外、传递依赖、网络传播、附加限制、专利、商标、署名和 NOTICE | 任一拟采用方式未知、不兼容或尚待专业审查时，只观察或改用其他方式；不得建议该方式 |
| OSS-G3 | 有可阅读的架构/开发文档和可定位源代码 | 缺一项则不得作为架构主参考 |
| OSS-G4 | 最近 12 个月有提交、稳定发布或维护组织的明确支持声明之一 | 无三类证据则判维护未知，不进入主榜 |
| OSS-G5 | 已按目标版本、支持期限、直接/传递依赖、容器和发布物范围检查官方安全公告、漏洞库、维护状态与披露渠道，并记录公告日期、修复状态和实际可利用性 | 证据不足一律标 UNKNOWN；存在未缓解关键风险或处于停止支持状态时禁止直接引入 |
| OSS-G6 | 能明确回答至少一个 A6 架构问题 | 只因“热门”而无对应问题则淘汰 |

### 7.6 100 分评分模型

| 维度 | 权重 | 核心证据 |
|---|---:|---|
| R-MOS 业务与规模匹配 | 25 | 对应功能、单校/边缘部署、机器人/教学边界、可裁剪程度 |
| 架构质量 | 20 | 模块责任、依赖方向、适配器、状态机、数据所有权和扩展点 |
| 成熟度 | 15 | 项目年龄、稳定版本、治理、文档、测试、迁移和兼容承诺 |
| 活跃度与新鲜度 | 15 | 12 个月提交、活跃贡献者、发布次数、问题响应和路线图 |
| 安全与供应链 | 10 | SECURITY、威胁模型、依赖锁定、发布签名、OpenSSF 结果 |
| 社区与采用 | 5 | 星标、分叉、被依赖、机构采用和贡献者分布 |
| 引入与迁移成本 | 10 | 技术栈差异、部署负担、数据迁移、人员学习和长期维护 |

其中高分表示与 R-MOS 更匹配、架构更清晰、项目更成熟活跃、安全治理更完整、采用更广且引入成本更低。

**活跃度 15 分量化：**

| 子项 | 分值 | 评分规则 |
|---|---:|---|
| 最近有意义提交 | 5 | ≤30 天 5 分；31–90 天 4 分；91–180 天 3 分；181–365 天 1 分；>365 天 0 分 |
| 近 12 个月稳定发布 | 4 | ≥4 次 4 分；2–3 次 3 分；1 次 1 分；0 次 0 分；滚动发布项目用官方维护记录等价取证 |
| 近 12 个月活跃贡献者 | 3 | ≥20 人 3 分；5–19 人 2 分；2–4 人 1 分；<2 人 0 分 |
| issue/PR 响应抽样 | 3 | 最近 20 个有效样本的首次维护者响应中位数 ≤7 天 3 分；8–30 天 2 分；31–90 天 1 分；>90 天或无证据 0 分 |

“有意义提交”指对源代码、测试、架构/运维文档或正式发布物产生可核实影响的非合并提交；纯格式、自动版本号、依赖机器人机械更新和仅合并分支不计。“有效样本”指研究截止日前最近关闭或仍开放的真实用户 issue/外部 PR，排除 bot、spam、重复项、纯公告和维护者自建占位项；不足 20 个时使用全部样本并降低证据可信度。

**成熟度 15 分量化：**

| 子项 | 分值 | 评分规则 |
|---|---:|---|
| 公共维护历史 | 4 | ≥5 年 4 分；≥3 且 <5 年 3 分；≥2 且 <3 年 2 分；≥1 且 <2 年 1 分；<1 年 0 分 |
| 稳定版本与兼容承诺 | 4 | 有稳定版本、版本策略、升级/迁移说明三项齐全 4 分；每缺一项减 1 分；无稳定版本 0 分 |
| 治理与责任连续性 | 3 | 有维护组织、治理说明、CODEOWNERS/等价责任机制三项齐全 3 分；每缺一项减 1 分 |
| 测试与发布质量 | 2 | 默认分支持续集成和可复现发布证据齐全 2 分；仅一项 1 分；均无 0 分 |
| 文档与采用案例 | 2 | 架构/运维文档和可核实生产采用案例均有 2 分；仅一项 1 分；均无 0 分 |

上述阈值先用于同一研究域、同一预定使用方式内的横向评分，不得把 LMS、机器人中间件、观测工具和策略引擎的总分直接互排。每个领域在首批 2 个样本后冻结领域校准说明，列出发布模式、合理贡献者规模和采用证据；成熟但低频维护的小型项目可保留原始分和领域说明，但不得手工改分。

每个评分项必须同时记录证据可信度：`HIGH`（官方且可复现）、`MEDIUM`（可信二手来源或有限抽样）、`LOW`（单一自述）、`UNKNOWN`（无证据）。`UNKNOWN` 按该子项 0 分，`LOW` 不得单独支持硬门槛。主审和独立复核者各自评分，单项差异超过该项满分的 20% 时必须校准并保留两版原分与裁决理由。成熟度、活跃度和社区采用分别只计其定义字段，禁止同一证据跨维度重复加分。

评分结论：

- 85–100：主参考候选，可进入 R1 对照；
- 75–84：次参考候选，只借鉴明确子领域；
- 60–74：思想参考，不得作为结构母版；
- 0–59：淘汰；
- 任一硬门槛失败：无论总分多少都不得成为主参考。

星标和最近更新时间只占辅助权重，防止“热门但不适合”或“频繁更新但不成熟”项目挤掉真正匹配的项目。

### 7.7 深度研究字段

每个候选项目至少研究以下字段：

**身份与来源**

- 项目名、官方组织、仓库、官网、基金会归属；
- 创建日期、首次稳定版本、当前稳定版本和发布日期；
- 仓库状态、默认分支、主要语言、代码规模。

**活跃度与成熟度**

- 最近提交、近 90/365 天提交趋势；
- 近 12 个月发布次数、稳定/预发布比例；
- 近 12 个月活跃贡献者和核心维护者集中度；
- issue/PR 首次响应和关闭时间抽样；
- 版本兼容、迁移指南、路线图、治理和 CODEOWNERS。

**架构与领域能力**

- 系统上下文、模块图、进程/部署拓扑；
- 模块责任、接口、调用方向和扩展机制；
- 数据所有权、身份、租户、角色和对象权限；
- 工作流、状态机、幂等、重试、恢复和审计；
- 设备/机器人模型、适配器、遥测、停止与异常语义；
- 教学、班级、作业、尝试、成绩、报告和证据语义；
- 测试层次、样例、基准、监控、备份和升级方式。

**安全、许可与供应链**

- LICENSE/SPDX、逐文件例外、商标、附加条款、专利、署名/NOTICE 和贡献者协议；
- 只借设计、复制代码、引入依赖、部署服务四种使用方式各自的兼容结论；
- 直接及传递依赖许可证、网络传播条款和冲突风险；
- 目标版本、支持期限、SECURITY、官方公告、漏洞库、披露流程、修复状态、实际可利用性和 OpenSSF 结果；
- 容器/发布物、签名、SBOM 和依赖更新机制。

**R-MOS 决策字段**

- 对应 A6 问题编号；
- 可直接借鉴、需简化借鉴、明确不借鉴；
- 只借设计、复制少量代码、引入库、部署服务四种方式的边界；
- 技术栈差异、数据迁移、运行成本和团队学习成本；
- 失败模式、退出策略和替代候选；
- 证据链接、采集日期和不确定字段。

R0 主审负责基于许可证原文和依赖清单形成初步兼容判断，不把它表述为法律意见。R1 若拟复制代码、引入依赖或部署服务，且存在强互惠、网络传播、双重许可、专利/商标、附加限制、许可证冲突或任何解释不确定，必须在批准采用前升级为专业法律审查；专业结论及适用版本进入正式证据。

### 7.8 R0 产出与通过条件

R0 必须产出：

- 完整候选清单和淘汰记录；
- 每项目结构化原始研究结果；
- 各研究域评分矩阵；
- 每个研究域 0–2 个主参考和最多 2 个次参考；没有项目通过硬门槛和阈值时，“零个合格主参考”是允许且应明确记录的正式结论；
- “借什么、不借什么、为什么”的边界表；
- 许可证与安全风险表；
- R1 必须决策的问题清单。

R0 是否通过取决于搜索是否达到路线饱和、取证是否完整、评分是否可复现和淘汰原因是否充分，不取决于是否一定找到推荐项目。没有原始结果、证据链接和淘汰原因的“推荐榜单”不得通过。

## 8. R1 目标架构方向方案边界

R1 只在 A6 和 R0 均通过后开始。R1 应决定：

- 产品保留边界和明确删除边界；
- 目标系统上下文与部署边界；
- 目标模块及唯一责任；
- 模块间允许的依赖方向；
- 核心数据所有权和主记录；
- 身份、权限、审批、审计、证据和机器人安全的统一底座；
- 哪些开源设计被采纳、简化或拒绝；
- 继续渐进改造、局部重写或整体重写的董事会决议；
- 未来详细计划必须遵守的迁移顺序和回滚原则。

R1 不提供逐文件任务、代码示例、详细人日或发布排期。

R1 还必须为性能、容量、离线能力、安全、数据完整性、恢复时间、恢复点、可用性和可观测性分别给出：需求编号、Must/Should、来源发现、目标值或明确 UNKNOWN、决策状态和验证方式。无法在 R1 定量的项目必须登记为详细计划前置调查，不能静默省略。

## 9. 改造与重写决策门

### 9.1 默认策略

在 A6 和 R0 完成前，默认决策是“保留现场、暂停常规改造、不得整体重写”。完成后，每个目标模块分别标记：

- KEEP：现状可保留，只补证据或小范围缺口；
- REFACTOR：责任正确但结构或实现需要重构；
- REWRITE_MODULE：模块责任保留，内部重新实现；
- REPLACE：使用成熟组件或新模块替换；
- DELETE：没有有效消费者、重复或不再符合产品目标；
- UNKNOWN：证据不足，禁止进入改造计划。

### 9.2 整体重写的必要条件

只有 A6 与 R0 同时提供证据，并由 R1 形成以下全部“方案级可行性包”，才允许把整体重写列为推荐方向：

- 已有旧系统维持原则和新旧并行验证原则；
- 已证明现有有效数据、审计证据和文件资产存在可完整迁移、逐项核对和回滚的路径；A6 提供资产与约束，R1 提供数据映射、核对标准、旧系统保留和回滚的架构级方案；数据不能安全迁移、核对或回滚时，整体重写直接禁止；
- 已完成渐进改造与整体重写的同口径粗粒度估算，公开假设、范围和误差。

这里的方案级可行性包只证明路线可行，不包含逐表步骤、逐文件任务、切换时刻、人员排班或正式演练脚本，因此不等同于详细改造计划。R1 批准后，P0 必须把它展开为可执行的数据迁移、并行核对、切换、旧系统保留和回滚计划；在代表性隔离演练与正式门禁通过前，不得进行任何不可逆切换。

满足安全前置后，下列三项至少满足 2 项，才允许把整体重写列为推荐方案：

1. 需要替换或局部重写的核心业务模块占比不低于 60%；
2. 目标功能与现有有效功能的可复用比例低于 30%；
3. 关键模块无法通过接口隔离，渐进替换会长期形成双写或安全缺口；

同时，只有在同口径估算显示渐进改造总成本超过整体重写的 125% 时，才能把整体重写列为首选；否则即使满足 2 项，也只能作为备选。整体重写始终需要单独董事会批准；不满足时默认采用模块级渐进改造。

## 10. 未来分层改造原则

详细改造计划虽然暂不编制，但未来必须按以下层级依次获批：

### L1 架构层

先批准系统边界、模块图、数据所有权、依赖方向、安全底座和部署拓扑。L1 未批准，不得改目录和代码。

### L2 模块层

逐模块批准责任、输入、输出、状态、依赖、数据、错误和验收边界。每次只迁移一个可独立验证的模块或一组强耦合模块。

### L3 文件层

在模块契约固定后，明确每个目录和文件的唯一职责、保留/移动/删除关系和兼容层。不得仅为“看起来整齐”移动文件。

### L4 代码层

先失败测试，再最小实现；每个提交只完成一个可验证目标；自动测试、浏览器、预生产、真机和课堂证据严格分开。

任何 L4 任务必须能追溯到一个获批的 L1 决策、L2 模块契约和 L3 文件责任，否则不得实施。
