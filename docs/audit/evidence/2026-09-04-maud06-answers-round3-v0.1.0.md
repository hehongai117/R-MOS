### A0-Q01

不能改写。后来的修复只能证明“现在发生了变化”，不能否定 `B-ASIS` 时点已经存在的事实。否则会抹掉风险曾经存在的时间段、修复来源和审计追踪关系。

三个时间边界分别回答：

1. `B-REF`：回答 Phase 3 干预前是什么状态。它用于确认入口原来是否存在、是否受保护，以及某项变化究竟是不是 Phase 3 引入的。

2. `B-ASIS`：回答正式审计基线时是什么状态。A4 对未鉴权入口的历史结论固定在这个提交上；如果当时入口存在且缺少保护，“当时不安全”就是历史事实。

3. 当前代码：回答经过后续删除或修复后，现在是什么状态。必须另建当前基线，重新检查入口是否真的消失、替代入口是否出现、相关权限是否完整、运行行为是否符合预期，然后把当前状态写成“已变化、待重验”或在证据充分后写成“当前已解决”。

边界条件还有：

- 当前修复不能自动关闭以 `B-ASIS` 为依据的发现，只能给该发现增加“历史成立、当前待复验”的状态。
- 删除一个入口不能证明同类入口全部安全，也不能证明运行环境、部署状态和权限链已经安全。
- `B-REF..B-ASIS` 的变化仍须分别关联原批准记录和本轮验证结果；进入现状基线不等于当初获批，也不等于已经验证。
- 正确做法是保留历史结论，同时增加当前代码的复验结论，而不是回写历史。

### A0-Q02

必须分开，因为两类对象回答的问题不同，关闭条件也不同。

26 个产品问题描述的是系统本身的缺陷或风险，例如权限、审批、机器人安全、恢复能力和数据边界。它们按照对角色、功能、数据和设备可能造成的影响分为 P0、P1、P2，并按唯一产品根因计数。

5 个治理阻断项描述的是审计能不能被正式信任和批准：

- AG-01：缺少完整、准确的批准链。
- AG-02：缺少合格的可理解性检查证据链。
- AG-03：P0 主、备用通知渠道和送达证据不完整。
- AG-04：环境指纹、阶段复比或精确分母不能复现。
- AG-05：当前代码已经漂移，但新基线和影响评估没有闭合。

这些治理项不是五个额外产品缺陷，也不能自然套用产品严重度。一个治理项可能同时使多个阶段或多个产品结论失效；一个产品问题修好，也不会自动补出批准记录、通知回执或环境指纹。反过来，审计材料补齐也不会自动修复产品问题。

如果合并成“31 个问题”并统一排序，会造成：

1. 被迫给治理缺口编造 P0/P1/P2，混淆“产品危害大小”和“证据是否可信”。

2. 产品风险统计被污染，P0/P1/P2 的数量不再代表真实产品根因。

3. 修复进度失真。代码修复可能被误认为同时关闭治理项，或者文档补齐被误认为关闭产品缺陷。

4. 责任和后续动作错配。产品问题需要代码、数据、运行或现场验证；治理项需要批准、独立复核、送达记录和基线证据。

5. 依赖关系丢失。治理阻断项影响的是阶段结论的有效性，不应作为一个普通功能缺陷排在产品待办队列中。

6. 高危产品问题可能被治理事项挤压或稀释，导致错误的整改优先级。

7. 可能出现“31 项已处理若干，因此审计接近完成”的假进度，甚至错误推动 A6、R0 或 R1。

因此，“26 个产品问题”和“5 个治理阻断项”可以同时报告，但必须保留两套分类、状态和关闭证据。

### A0-Q03

解除 HTTP 路由结论的暂停，需要出现同一冻结提交、同一环境下可复现的双源证据：

1. 静态枚举必须按“最终完整路径、最终挂载前缀、HTTP 方法”形成路由身份，不能只比较装饰器中的局部路径。

2. 运行时必须从实际加载后的路由表或 OpenAPI 导出完整原始清单。

3. 必须事先冻结业务路由、框架路由、挂载路由等纳入和排除规则。

4. 两份原始输出、比较程序、执行命令、提交、环境、时间和退出结果都要保存。

5. 所有差异都必须逐项解释并归并；只有最终差集为零，才能重新形成“静态与运行时一致”的结论。

6. 动态挂载、条件注册和依赖加载必须人工复核，不能再次只靠字符串匹配。

后来的 A0 当前路由快照只能作为新证据输入；如果它不是针对 A1 冻结基线完成的完整双源复比，就不能自动恢复 A1 原来的结论。

要把 WebSocket 从 `UNKNOWN` 改成确定结论，需要证明“后端入口存在”和“真实消费者能够或不能到达它”：

1. 从运行时后端路由表导出全部 WebSocket 入口。

2. 从前端源码和实际构建产物枚举全部消费者，并解析动态拼接的地址、前缀、参数和环境变量。

3. 对静态扫描无法判断的动态路径逐项人工复核。

4. 在受控环境中，从真实页面或客户端动作发起连接，保存浏览器网络记录、握手结果、关闭码、服务端日志和消息收发结果。

5. 证明连接是由哪个页面、哪个用户动作、哪个身份和哪个对象触发的，而不只是某个测试客户端能单独连接。

6. 若要判定“不可达”或“无消费者”，必须证明所有已构建入口和规定流程均未产生连接，并有第三种独立证据支持；仅搜索不到字符串仍不能下结论。

这些证据出现后，WebSocket 才能从 `UNKNOWN` 改为“已证实可达”或“已证实无可达消费者”，而不是默认改成通过。

### A0-Q04

两半必须分开，因为它们是两个不同强度的命题。

“代表性 FACT”只需要找到一个或多个可以直接定位的反例，就能证明：确实存在写入口没有取得调用者身份，或者没有执行所需的对象范围检查。即使总数暂时不知道，这个根因仍然成立。

“精确计数”要求完整、稳定、可复现的分母：哪些入口算写操作、最终完整路径是什么、全局保护和端点保护怎样计算、动态挂载怎样处理、何种范围检查才算有效、哪些对象本来就没有所有者字段。生成脚本、输入、排除规则和原始输出缺一不可。旧枚举没有满足这些要求，所以应暂停数字，不能因此删除已经证实的根因。

只保留“94 条写操作仅 10 条有归属校验”会产生以下具体误导：

1. 它让人误以为剩余 84 条都是同一种“忘记加检查”的代码错误，可以批量补同一个保护条件。

2. 实际上，有些对象存在明确所有者字段，适合做对象级检查；另一些数据表根本不记录所有者，需要先决定增加字段和迁移历史数据，还是采用经过批准的角色规则。两者不是同一种改法。

3. 部分入口可能需要个人所有权，部分需要学校、教师—学生、班级或机器人范围，还有部分可能只允许管理员。单一数字掩盖了权限语义差异。

4. 给无所有者字段的入口增加“教师可写”之类角色保护，只能作为过渡措施，不能证明教师之间已经隔离，也不能证明提交者与批准者已经分离。

5. 它会把计划错误地排成“给 84 个入口加守卫”，遗漏数据结构变更、历史空值处理、迁移、职责分离和逐域负向测试。

6. 它会制造错误的进度指标。保护条件数量增加，不等于对象级越权风险按同样比例下降。

7. 它会扭曲工作量、优先级和验收分母，并可能在仍有代表性反例时错误宣布 M-01 已关闭。

后续改造记录已经证明这种误导真实存在：一部分入口能够补对象级检查，另一部分只能先采用角色限制，后者仍然缺少对象级隔离。因此应保留根因，重新建立逐入口、逐对象类型的完整矩阵，再计算新分母。

### A0-Q05

两者的根本差别是：机器人资产管理处理“系统里关于机器人的数字对象”，机器人运动控制处理“对真实设备施加动作”。

机器人资产管理通常包括：

- 机器人型号和元数据的登记、查询、修改和删除。
- 文件上传、下载和存储。
- URDF、CAD、GLB、清单和三维模型的解析、转换与展示。
- 资产权限、持久化和页面交互。

机器人运动控制及急停则至少涉及：

- 明确的运动指令和参数契约。
- 身份、对象范围、风险等级和审批。
- 指令状态、设备确认、超时、失败、重试和去重。
- 遥测与实际动作的一致性。
- 正常停止、异常停止、断网行为和失联后的安全状态。
- 软件停止与现场物理联锁、物理急停之间的边界。
- 真实机器人安全区中的 E3 验证，包括停止是否真的生效及其时延。

所以，即使资产页面、资产接口和自动测试全部通过，也只能证明对应提交和环境中的资产链路达到其证据上限。它不能证明系统存在产品级运动控制契约，更不能证明急停能够让真实设备进入安全状态。

当前审计仍将机器人控制和异常停止标为 `MISSING`，将真机证据标为 E3 `BLOCKED`。模拟适配器、三维动画、关节状态显示、故障注入或资产 CRUD 都不能替代真实运动控制和急停证据。

要认定运动控制和急停可用，必须另行完成控制入口、权限与审批、审计、状态机、失败处理和安全契约，并在获批安全环境中取得真实机器人及物理安全边界的证据。

### A0-Q06

要推翻“审批设施没有完整进入真实执行路径”，必须出现一条从真实用户入口一直贯穿到真实动作、持久化状态和审计记录的完整证据链，而不是只证明审批类、审批表或审批页面存在。

需要证明：

1. 真实入口确实进入审批路径。前端或调用方发起一个需要审批的动作后，系统必须创建与原请求绑定的持久化审批记录，而不是绕到另一套内存队列。

2. 审批前绝不执行。请求进入 `pending` 后，实际分派器和真实写动作都没有被调用，外部状态、数据库和设备均无副作用。

3. 审批对象不可被替换。审批记录必须绑定原始命令、工具、参数、对象、风险、证据和预期副作用；批准时执行的必须是同一个不可篡改的请求。

4. 批准后执行真实动作。合法且有权限的批准者将状态从 `pending` 改为 `granted` 后，系统执行一次真实动作，并能观察到预期结果。返回一个“写入成功”的模拟结果不够。

5. 拒绝后永不执行。状态从 `pending` 改为 `rejected` 后，真实动作调用次数必须为零，相关命令进入明确终态，并留下拒绝原因和审计记录。

6. 重复批准不重复执行。连续或并发发送相同批准请求，只允许一次状态变化和一次真实副作用；其余请求必须成为无变化的幂等结果。

7. 重复拒绝不产生额外动作。重复拒绝不得改变已经确定的结果，也不得触发写操作。

8. 冲突操作被拒绝。已拒绝后再批准、已批准后再拒绝，都必须被阻止，且不能产生第二次执行。

9. 重试和恢复仍然安全。网络重试、服务重启、工作进程重试或消息重复投递后，也不能重新执行已经成功的动作。这需要持久化的唯一性和并发证据，不能只验证单进程顺序调用。

10. 全链路可回放。命令、工具调用、审批、批准者或拒绝者、时间、原因、执行结果和审计事件应共享同一追踪标识，并能证明每一步的先后关系。

11. 所有真实入口都受控。不能只修一条路径，而让另一种请求模式、旧接口或直接工具入口绕过审批。

当前后续改造只提供了部分证据：需要审批的请求已经能在分派前被拦住，非审批请求仍能正常分派，部分请求也会建立持久化记录。但前端仍固定使用单一请求模式，批准后调用的仍是不会产生真实外部副作用的模拟执行器。因此现有证据还不能推翻 A4 的完整结论。

如果审批的对象是机器人动作，除上述证据外还必须取得 E3 真机安全证据；普通自动测试不能替代。

### A0-Q07

`E2_NOT_COLLECTED` 表示：当前没有新鲜、合格的 E2 运行证据，因为本轮没有执行对应采集。它通常表示采集尚未安排、尚未批准或尚未运行；若环境和条件具备，可以按受控方案补采。它不表示能力已经通过，也不必然表示能力已经失败。

`E2_BLOCKED` 表示：当前存在已知前置障碍，无法安全地执行采集，或者即使执行也不能形成合格证据。例如：

- 正式备份能力本身尚未建立。
- 没有可证明等价的环境。
- 恢复、回滚或断网演练缺少前置方案。
- 生产或真机门禁仍生效。
- 必要授权、隔离或安全条件未满足。

因此，`BLOCKED` 不只是“还没测”，还说明必须先清除障碍；但它同样不能被自动解释成运行失败，除非另有直接失败证据。

A5 报告审计的是“现有证据到底能证明什么”。所以原则上，即使一些运行能力没有 E2，A5 也可能因为以下事项做得真实、完整而获批：

- 每项运行能力都明确标为 `E2_COLLECTED`、`E2_HISTORICAL`、`E2_NOT_COLLECTED` 或 `E2_BLOCKED`。
- 没有把配置、脚本、旧测试数字或历史记录冒充当前运行成功。
- 每个 PASS 都能追到提交、环境、命令、原始输出和退出结果。
- 无法复现的结论已经降级。
- 没有隐含空白或越级外推。

但这种批准只表示“A5 对证据边界的描述可信”，不表示系统的迁移、服务启动、恢复、回滚、断网、真机、课堂或生产能力通过。

其后果仍然是：

- A6 的相应维度必须保持 `UNKNOWN/BLOCKED`。
- R1 不能据此作绑定性的路线决策。
- E3、E4、生产启用和 `REL-BLOCK-01` 不会提升。
- 各项能力仍须在相应环境中分别取证，不能互相替代。

当前 A5 正式报告本身仍为 FAIL；“可能获批”是治理规则允许的结果，不是当前状态。

### A0-Q08

第一个是计数和内部一致性错误；第二个是事实归属和因果关系错误。

“声明 25 个、表中实际 26 行”说明汇总数字没有从台账机械复算。它会破坏问题总数、P1 数量、覆盖率和进度分母，但每一行问题及其证据仍可能单独存在。该错误通常可以通过解析表格、检查唯一编号、按严重度重新计数来发现。

“把两套审批实现的属性写反”则是把“哪套有消费者、哪套使用内存、哪套进入实际路径”判断错了。实际使用内存队列的是没有消费者的旧实现，而不是被实际引用的那套。这个错误会导致：

- 错判审批状态是否持久化。
- 错判哪套实现能够被真实入口调用。
- 把死代码当成实际风险路径，或把实际断点藏在错误实现后面。
- 删除错误的实现、保留真正的旁路，或者按错误方向设计整改。
- 错误评价重启、并发、审计和审批绕过风险。

因此第二个更危险。第一个主要破坏总表可信度和规划分母；第二个会直接改变对系统行为、根因和整改对象的判断，即使所有数字都正确，仍可能作出相反的架构或安全决策。

新增的机械检查脚本能够防住第一个错误，因为它会：

- 从产品问题表实际解析各个 Master 行。
- 检查重复编号。
- 复算总数以及 P0、P1、P2 数量。
- 比较报告声明数字和台账实际数字。

所以它能发现“25 对 26”和“P1 10 对 11”。

该脚本防不住第二个错误。它只检查文本结构、数字、路径和状态标记，不会分析源码调用关系，也不会判断一句话中的属性是否绑定到了正确实现。要防住属性写反，必须沿真实用户入口正向检查消费者、调用图、状态存储和执行路径，并由异源复核者重新核对。

### A0-Q09

必须取得新鲜、可复现、与具体提交和交付环境绑定的实际运行证据；工作流文件、脚本和配置只能证明“有人打算这样运行”。

PostgreSQL 迁移至少需要：

1. 使用真实 PostgreSQL，而不是 SQLite 或测试中的 `create_all`。

2. 固定数据库版本、扩展、初始迁移状态、目标提交和依赖指纹。

3. 在空数据库以及需要支持的旧版本数据库上实际执行迁移。

4. 保存完整命令、原始日志、时间和退出码。

5. 验证迁移头、最终结构、约束、关键数据完整性和重复执行行为。

6. 证明工作流中的环境变量没有被重复配置覆盖，实际使用的确是声明的 PostgreSQL。

服务启动至少需要：

1. 使用与交付一致的构建物、配置和依赖实际启动前后端及所需服务。

2. 执行完整启动生命周期，而不是只导入应用对象或让静态页面返回 200。

3. 保存启动日志、监听端口、就绪结果、进程状态和退出结果。

4. 验证依赖正常时健康检查通过，数据库等关键依赖异常时健康检查返回正确的失败状态，不能仍然返回 200。

端到端流程至少需要：

1. 在上述真实服务和 PostgreSQL 环境中，从浏览器或正式 API 入口运行规定流程。

2. 覆盖真实身份、权限、数据库写入和关键失败路径，不使用模拟响应代替主链路。

3. 保存浏览器记录、请求与响应、服务日志、数据库结果、测试报告和最终退出码。

整套证据还必须记录提交、环境等价性、命令、输入、执行时间、原始输出、清理结果，以及远程工作流的运行编号或链接。三类能力要分别证明，不能用“迁移成功”推导“服务和端到端流程成功”。

A0 后来的数据库只读快照、前端入口返回 200，以及改造后的大量自动测试，都不足以单独推翻这个结论：前者没有执行迁移、后端生命周期或业务流程；后者也不等于在交付配置下完成 PostgreSQL 和浏览器端到端运行。

即使取得合格 E2，它也只证明对应提交、对应环境和对应执行；不能倒改 `B-ASIS` 的历史结论，也不能自动外推到生产、真机或课堂。
