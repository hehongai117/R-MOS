### 1.3.1 C-0：急停的最小正确序列（P0，取代原 C-1+C-2）

原方案「置 `EMERGENCY` 状态位 + 清空队列」**不足以构成停止**。正确的最小序列：

1. **急停状态锁定**（latch，不可因后续事件自动解除）
2. **拒绝新动作**（此后所有控制请求返回拒绝）
3. **使未发送动作失效**（清本地队列——这是 openTCS `clearCommandQueue` 真正保证的部分）
4. **向控制器发出取消/停止请求**（已送达的命令只能靠这一步）
5. **等待并记录确认**——「已停止」或「安全回路已激活」
6. **经授权且现场条件满足后才允许解除**（人工复位，非自动）

> **第 4、5 步是原方案完全缺失的**，也正是「清队列即停止」这个误读掩盖掉的部分。
> 没有第 5 步的确认，系统无法区分「已停止」与「发过停止指令但不知道停没停」。

### 1.4 借什么 / 不借什么

**借（设计层）：** C-0（P0）、C-3~C-9 按上表订正后的表述。

**明确不借：**

| 不借 | 理由 |
|---|---|
| ROS 2 / JVM 运行时与消息模型 | 技术栈与规模不符 |
| 实时性设计、交通调度、路网模型 | R-MOS 无此需求 |
| **「ros2_control 有急停原语」** | 出处为演讲材料非契约文档，`[uncertain]` |
| **~~「清队列即停止」~~** | **0.1.0 的错误结论，已删除** |
| **C-9 用于急停** | 析构自动恢复，与急停的闩锁语义相反 |

### 1.5 失败模式（R1 必须避免）

1. **假急停 I**：只置状态位不做任何指令层动作。
2. **假急停 II（0.1.0 主审自己犯的）**：置状态位 + 清本地队列就认为停住了——
   **已送达控制器的命令不受此保证**，必须显式发取消并等确认。
3. **抄枚举不抄迁移规则**：定义了 `EMERGENCY` 却没定义谁能置位、置位后拒绝什么、如何解除。
4. **用自动恢复语义实现急停**：如直接套用 Open-RMF 的 `Interruption`（析构即恢复）。
5. **把业务通信协议当安全回路**：VDA 5050 明确声明自身不是安全标准。
