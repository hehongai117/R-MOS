# R0 决策边界矩阵

- 版本：0.2.0
- 日期：2026-08-30
- 状态：NON_BINDING / RETURN FOR REVISION

## 1. 机器人停止与安全责任分层

这不是“急停执行序列”，而是责任边界：

| 层 | 可以承担 | 不能承担 |
|---|---|---|
| 物理与安全层 | 依据适用标准、风险评估、厂家资料、安全控制器和物理急停实现安全功能 | 不能由普通 WebSocket、HTTP、消息队列或 AI 代替 |
| R-MOS 控制层 | 观察安全状态后抑制新命令、禁止超时自动重发、冻结自动流程、记录审计并提示人工处置 | 不能把软件确认当作物理停止已经生效的证据 |
| 业务协议层 | 尽力取消订单、收敛业务状态、处理不可取消动作和回执 | 不能把 `cancelOrder`、暂停或队列清空称为急停 |

VDA 5050 只进入第三层；OPC UA Robotics 在本轮只用于第二层的状态词汇；ISO 13850、ISO 3691-4 以及厂家安全资料才可能进入第一层的适用性判断。

## 2. 借什么、不借什么

| 对象 | 可保留的原子事实/设计 | 明确不借 | 原因 |
|---|---|---|---|
| ros2_control | 生命周期、硬件接口、控制器责任分离 | 用停用生命周期冒充急停；整套 ROS 运行时 | 无安全额定急停证据；体量不匹配 |
| Open-RMF | 车队适配器与状态上报词汇 | 把 emergency 状态枚举当安全执行；自动恢复用于急停 | 状态上报不等于安全动作 |
| openTCS | 车辆通信适配器和队列边界 | 把清队列/暂停当急停；依据许可证目录推断适用许可证 | 控制语义和许可证适用均需逐项证据 |
| Eclipse Ditto | 对象策略、当前/期望状态、订阅概念 | 直接引入分布式 JVM 平台 | 当前单校单机边界不匹配 |
| ThingsBoard CE | CE 源码可证明的租户、遥测和规则概念 | 用 PE 文档证明 CE；直接部署整套平台 | 版本/授权边界和体量不匹配 |
| OpenRemote | 资产、realm 和协议代理概念 | 未经专业审查复制、依赖或部署；断言整个 R-MOS 必然 AGPL | covered work 与组合边界需具体分析 |
| VDA 5050 | 订单取消和动作状态语义 | 急停、安全标准、所有取消动作必报 FAILED | 官方规范明确安全边界和不可取消动作行为 |
| OPC UA Robotics | 急停与防护性停止分开的状态模型 | 行业唯一性、物理执行、安全合规充分性 | 本轮只证明信息模型且范围限所审对象 |

## 3. 许可证与安全风险

| 对象 | 当前风险 | 允许方式 | 禁止/待审方式 |
|---|---|---|---|
| openTCS | 完整逐文件与依赖映射未完成；无证据支持“项目含 LGPL 映射” | 只借设计 | 复制、依赖、部署待逐文件和专业审查 |
| OpenRemote | AGPL 与组合边界复杂 | 只读观察设计 | 复制、依赖、部署和“整体受 AGPL”结论均待专业审查 |
| ThingsBoard CE | CE/PE 来源混淆、未知模板和依赖未审 | 固定 CE 源码中的设计观察 | 复制、依赖、部署待审 |
| 其余三项软件 | 目标版本安全与供应链证据不足 | 非绑定设计观察 | 复制、依赖、部署不得建议 |
| VDA/OPC/ISO | 适用性、版本和实现合规边界 | 规范解释与术语边界 | 不得代替厂家安全层、风险评估或正式合规判断 |

## 4. R1 必须决定的问题

1. R1-Q1：按每种机器人类别、厂家安全接口和适用标准，物理急停、保护停止、业务取消、状态观测和审计分别由谁负责？
2. R1-Q2：所有命令如何在安全状态未知、超时、断网和重连后保持默认拒绝且不自动重发？
3. R1-Q3：设备/机器人对象、订阅授权、租户/学校边界和跨实例广播的唯一主记录是什么？
4. R1-Q4：审批怎样成为执行前的阻塞闸门，并与身份、对象归属、审计和恢复状态贯通？
5. R1-Q5：备份、恢复、回滚、证据时间线和监控分别采用什么最小组合，如何满足 E2？
6. R1-Q6：任何开源代码、依赖或服务采用前，谁负责目标版本安全、许可证与退出策略批准？

这些问题当前只是清单。A6 和 R0 未通过前，不形成绑定性路线决定。
